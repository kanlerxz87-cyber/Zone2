How to use this page

Every row below is a proposal, not a change that has been made. Each one states the problem it solves, the options and what each costs, a recommendation, and the official source the reasoning rests on. The Decision cell is deliberately blank: it is where the reviewer records accept, reject or defer, and until it is filled the suggestion has not been approved.

  1. Read the Decision table below and pick the rows that matter to you.
  2. Open the detail for each one — the options and the trade-offs are where the real choice is.
  3. Fill in the Decision cell, in the table or in the detail card.
  4. Anything still unanswered belongs in the open-questions register, which lists what is missing and how to obtain it.

Nothing here is a product claim. A suggestion that rests on a number carries the source of that number; a suggestion that rests on a judgement says so.

S-01

Confirm the three target products from inside the Amazon Associates account

Impact: Blocking Effort: Low Needs decision Phase: Phase 1 — unblock launch

The problem

The three supplied codes are 9 characters each. Amazon's own help page defines an ASIN as a 10-character identifier, so a supplied code is not an ASIN. Following each code does resolve to exactly one Amazon listing, and the destination has stayed the same across every check since 2026-11-13 - but no public Amazon document binds a link.amazon code to a product. The site can therefore say what each code points at, and never what the brief asked for.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option AOpen each of the three codes in the Associates account's own link checker and read the destination ASIN from there.Needs about five minutes of the account owner's time. It removes the ambiguity permanently and gives the site a citable Amazon-side confirmation.
Option BPublish against the three destinations that were observed, describing them as 'the product this link resolves to'.Zero owner time and already true of the live site, but if the brief meant different products then every published article is about the wrong item and the content has to be rewritten.
Option CTreat the codes as place-holders and rebuild the product set from a fresh niche-research pass.The cleanest end state, and the most work: it needs the licensed catalog access described in S-03, which is not available yet.

Recommendation

Take option A, and keep option B as the published wording until A's answer arrives. Option A costs five minutes; option C costs a quarter.

What this rests on

  • S24affiliate-program.amazon.com — Amazon's ASIN and link-format help: an ASIN is a 10-character identifier.
  • S33link.amazon — Supplied code 1 - the link this repository follows.
  • S34link.amazon — Supplied code 2.
  • S35link.amazon — Supplied code 3.
  • S19www.amazon.com — Destination listing observed for code 1 on 2026-11-15.

S-04

Decide the niche: Air Fryers, or countertop cooking appliances?

Impact: Blocking Effort: Low Needs decision Phase: Phase 1 — unblock launch

The problem

All three resolved destinations sit in one Amazon category - Home & Kitchen, Kitchen & Dining, Small Appliances, Fryers, Air Fryers - and the category breadcrumb was read directly off each listing on 2026-11-15. A single-category portfolio is too narrow to support a hub-and-spoke content cluster, and the platform's own niche-discovery module exists to answer exactly this question but has no keyword data to score with.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option AKeep the three products, but set the content niche one level wider - countertop cooking appliances - so there is room for a topic cluster around them.No new data needed, and the products stay relevant. Risk: the wider niche has more competition, which cannot be measured until a keyword source exists (Q-13).
Option BKeep the narrow Air Fryers niche and win on depth rather than breadth.Cheapest to execute and honest about what the evidence supports, but a three-product niche has a small ceiling.
Option CRun a formal niche score - search volume against competition against commission - before writing anything.The most rigorous answer, and it needs a keyword source and a commission band per category, neither of which is available yet.

Recommendation

Option A. It keeps the products, gives the editorial calendar room to breathe, and needs no data the project does not have. Revisit with option C once Q-13 is answered.

What this rests on

  • S19www.amazon.com — Category breadcrumb read off listing 1 on 2026-11-15.
  • S20www.amazon.com — Category breadcrumb read off listing 2 on 2026-11-15.
  • S21www.amazon.com — Category breadcrumb read off listing 3 on 2026-11-15.

S-02

Re-issue the three links as tagged Special Links before publishing anything that links out

Impact: Blocking Effort: Low Needs decision Phase: Phase 1 — unblock launch

The problem

None of the three resolved URLs carries an Associates tag parameter. The Program Policies make the tag the mechanism by which a click is attributed to an associate, so as supplied these links cannot attribute a purchase and cannot earn a commission. The repository already refuses to invent a tag and labels every outbound link as a non-earning preview link; that is the correct behaviour, but it means the site as it stands earns nothing.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option AGenerate Special Links for the three confirmed ASINs with the account's own link-creation tool, and paste the tag into the site configuration.The account owner has to do it once. Nothing else on this list has value without it.
Option BHave the link builder append the tag to every outbound link at build time from a single configured value.One place to change, and the build can refuse to publish a link with no tag - which is the behaviour the repository already models for preview links.
Option CLeave the links untagged and treat the site as a non-commercial demonstration.Nothing to decide and nothing to earn. Fine for a portfolio site; pointless for an affiliate business.

Recommendation

Option A for the three launch products, then option B as the general mechanism, with the build failing if a published link has no tag.

What this rests on

  • S02affiliate-program.amazon.com — Participation Requirements: the Associates ID must be a URL parameter on the link.
  • S29affiliate-program.amazon.com — The same section, read directly for the tagging rule.
  • S09affiliate-program.amazon.com — Amazon's own tools page - where Special Links are created.

S-12

Keep publishing no prices, and say plainly why

Impact: Medium Effort: Low Proposed Phase: Phase 2 — first 30 days

The problem

The Program Policies restrict displaying prices to links Amazon serves and to licensed API data. The site currently prints no product price at all and enforces that with a deploy gate, which is stricter than the policy requires. That is defensible, but a reader comparing three products is left without the one number they came for, and a competitor who publishes prices will be easier to click.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option AKeep the no-price rule and make the reason visible on the comparison page, with the price available on the linked Amazon page.Fully compliant and honest, but it costs some comparison-driven clicks.
Option BPublish prices from the Creators API once S-03 gives access, which the policy permits.The comparison page becomes genuinely useful. It also creates a stale-data problem and a second failure mode the deploy gate would have to understand.
Option CPublish prices scraped from public pages.Not permitted, and it violates the site's own no-inference rule. Rejected.

Recommendation

Option A now, option B when the API exists. A static price pasted into a page is wrong within hours, which is why the current rule exists.

What this rests on

  • S02affiliate-program.amazon.com — Program Policies, price display rule (Participation Requirements).
  • S29affiliate-program.amazon.com — The same rule read directly.

S-13

Add the privacy policy and cookie notice the program and the FTC expect

Impact: High Effort: Low Proposed Phase: Phase 2 — first 30 days

The problem

The site carries the mandated affiliate disclosure on every page, but it has no privacy policy, no cookie notice and no contact route. The FTC's endorsement guidance treats a material connection that is not clearly and conspicuously disclosed as a violation, and disclosure has to sit close to the recommendation - which is what the link-level disclosure on this site does. A privacy policy is the place to say what the site collects and what it does not.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option APublish a privacy policy, a cookie notice and a contact page before the site takes traffic.One page each. If the site later adds analytics, the notice has to change - so write it now to describe what is actually true, which is 'no analytics, no cookies of our own'.
Option BRely on the affiliate disclosure alone.The disclosure is the program's requirement and it is met. It is not the whole of what the FTC's material-connection standard asks for, and it is not a substitute for a privacy policy.

Recommendation

Option A. It is cheap, and the site's current position - no tracking of its own - makes the notice short and easy to keep true.

What this rests on

  • S10www.ftc.gov — FTC Endorsement Guides: material connection must be disclosed clearly and conspicuously.
  • S11www.ftc.gov — FTC Disclosures 101 - how to make a disclosure work.

S-14

Give every agent a name and let it identify itself in the request it makes

Impact: Medium Effort: Low Proposed Phase: Phase 2 — first 30 days

The problem

Amazon's Agent Terms require an agent to identify itself with a User-Agent of the form Agent/[name], to not conceal that it is an agent, and not to attempt to defeat a human-check measure. Every automated fetch this project performs - and every automated fetch a future trend-detection module would perform - is in scope.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option ASet a single agent name in the link builder and the fetcher, and have it send Agent/[name] on every request.None that matters. It is a one-line configuration and it removes a compliance question from every future automation.
Option BRely on the fact that the fetches are low volume and harmless.Volume is not the test; the terms require identification.

Recommendation

Option A. It belongs in the same place as the link builder, so no future module can bypass it.

What this rests on

  • S30affiliate-program.amazon.com — Associates Program IP License and Usage Requirements, Agent Terms.
  • S02affiliate-program.amazon.com — Program Policies, incorporated by reference into the Agreement.

S-15

Set a sub-tag scheme that is per page, never per person

Impact: Low Effort: Low Proposed Phase: Phase 2 — first 30 days

The problem

The Participation Requirements permit a sub-tag for tracking but forbid tying a sub-tag to a specific end user. Nothing in this repository sets a sub-tag today, so there is no violation - but a growth plan that wants to know which article earns will reach for one immediately, and the rule that constrains it is easy to get wrong.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option ADefine the scheme now: one sub-tag per content type, never a parameter that varies per reader.Coarse attribution. It answers 'which article' and not 'which visitor', which is the right line to sit on.
Option BNo sub-tags at all.Simplest and safest, but then the click report cannot distinguish an article that earns from one that does not.

Recommendation

Option A, written into the link builder so the rule is enforced by the build rather than remembered by whoever edits content next.

What this rests on

  • S02affiliate-program.amazon.com — Program Policies: the Associates ID must be a URL parameter; a sub-tag may never be tied to a specific end user.

S-28

Keep the ambiguity visible instead of resolving it with a plausible guess

Impact: Medium Effort: Low Already the published behaviour Phase: Phase 3 — scale

The problem

Three official pages in this project disagree with each other: the Emeril page contradicts itself about its preset count, the Chefman 8 Qt page and the Amazon listing for the same product disagree about maximum temperature, and the three supplied codes resolve to products the brief never named. The tempting move - publish the most likely value and move on - would be a guess published with the authority of this repository. The project has instead left the conflict on the page.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option AKeep publishing every conflict as a conflict, with both statements and both sources, and keep the review page public.Some pages look unresolved. That is accurate, and it is the reason this site can be trusted on the rows where there is no conflict.
Option BResolve each conflict by precedence - manufacturer over marketplace - and say so once.Cleaner to read. It is also a decision this repository has no authority to make, and it would make the rows that agree look decided for the same reason.

Recommendation

Option A. A conflict on the page is a small cost; a guessed value published as fact is a large one, and it is the defect this entire repository exists to prevent.

What this rests on

  • S27www.emerileveryday.com — The Emeril page states 25 pre-sets in one place and 24 in another - both read 2026-11-15.
  • S26chefman.com — The Chefman 8 Qt manufacturer specification: 200-400 F.
  • S21www.amazon.com — The Amazon title for the same ASIN says 450 F.
  • S24affiliate-program.amazon.com — The ASIN rule that makes the supplied-code ambiguity unresolvable from a public page.

S-06

Publish original how-to and safety content that stands on its own without a product link

Impact: High Effort: Medium Implemented in this session Phase: Phase 2 — first 30 days

The problem

Google's spam policies describe 'thin affiliation' as publishing affiliate content where the product descriptions are copied from the merchant with no added value, and name 'original product reviews, rigorous testing and ratings, navigation of products or categories, and product comparisons' as the things that make an affiliate page good rather than thin. The United States Department of Agriculture publishes exactly the kind of material that adds value and cannot be copied from a merchant: how an air fryer works, what it must never be asked to cook, and the safe internal temperatures a thermometer has to read.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option APublish a cooking-safety and technique layer sourced from the USDA pages, linked to the products only where the product genuinely answers the question.Needs a named author and an editorial standard, because the guidance is explicit that the content must be authored and integrated. The material already exists and needs no invention.
Option BKeep every page product-led and rely on the comparison table as the added value.Fastest, but the comparison table is three rows wide - thin by the definition above.
Option CGenerate articles at volume from a template with the product name swapped in.This is the failure mode the policies name by name - 'using generative AI tools or other similar tools to generate many pages without adding value for users'. Listed so it is visibly rejected.

Recommendation

Option A. This session published the first two pieces of that layer, with every factual sentence carrying the government source it came from.

What this rests on

  • S38developers.google.com — 'Thin affiliation' definition and the list of what makes an affiliate page good.
  • S41www.fsis.usda.gov — USDA FSIS on how air fryers work, cooking times and temperatures, and what must not be air fried.
  • S42www.foodsafety.gov — The safe minimum internal temperature chart.

S-08

Build the site around a topic hub with spokes, not a list of standalone pages

Impact: Medium Effort: Low Implemented in this session Phase: Phase 2 — first 30 days

The problem

The site currently publishes three product articles, a buying guide and a comparison. They link to each other, but there is no hub page that states what the site covers, and no spoke that exists to answer a question someone would actually type. A hub makes the coverage legible to both a reader and a crawler, and it is the structure Google's own documentation assumes when it describes 'navigation of products or categories' as added value.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option AOne hub page per topic area, each listing its spokes, with the hub and the spokes cross-linked both ways.A structural habit rather than a one-off task. It costs a page per topic and it needs the niche decision from S-04 first.
Option BKeep publishing standalone articles and rely on the sitemap for discovery.Cheapest. It leaves the topical structure implicit, which is exactly what a reader (and a reviewer) cannot see.
Option CGenerate a hub per keyword.Scaled content abuse again - many pages with little value added. Rejected.

Recommendation

Option A. This session added a topics hub to the marketing set and made it the navigational spine of the front door.

What this rests on

  • S38developers.google.com — Added value for affiliate pages includes 'navigation of products or categories'.
  • S39developers.google.com — 'Does the content provide a substantial, complete, or comprehensive description of the topic?'

S-10

Publish a sitemap and register the property in Search Console

Impact: Medium Effort: Low Proposed Phase: Phase 2 — first 30 days

The problem

The site publishes roughly ninety pages across five namespaces and ships no sitemap. Google's sitemap documentation describes the XML format, the best practices, and the two submission routes - Search Console and a robots.txt reference. Without it, discovery depends entirely on links between pages.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option AGenerate sitemap.xml from the same build that produces the pages, and reference it from robots.txt.Needs a domain that is not a github.io subdomain to be worth doing properly, but the sitemap itself is valid wherever it is served.
Option BSubmit the sitemap in Search Console as soon as the property is available.Requires ownership of the domain and an account; it is a one-off task with a real payoff because it reports coverage and query data.
Option CSkip the sitemap and rely on internal linking.Works for a handful of pages. Not a plan for a site that plans to grow.

Recommendation

Options A and B together. The sitemap is cheap and mechanical; Search Console is what turns 'we published' into 'we can see what was indexed'.

What this rests on

  • S40developers.google.com — Google's sitemap documentation: formats, best practices, and submission via Search Console and robots.txt.
  • S22docs.github.com — GitHub Pages API - the source of truth for what is actually deployed.

S-26

Option CPublish the same article template per product per month.Scaled content abuse. Rejected.

Option A now, option B once Q-13 has a trend source. The calendar is real and it does not require a number this repository does not have.

What this rests on

Recommendation

Option A, with an honest statement of how the content is produced. The Amazon Agent Terms already require an agent to identify itself, so the author line is a disclosure either way.

S-16

Give every page one job and one call to action

Impact: Medium Effort: Medium Proposed Phase: Phase 2 — first 30 days

S-22

Decide the three numbers that will be used to judge every change

Impact: Medium Effort: Low Proposed Phase: Phase 2 — first 30 days

The problem

Right now nothing on this site has a performance figure, and no target exists. Without a target, 'is this change good?' is answered by opinion - which is how a site ends up optimised for the wrong thing. The program's own agreement is explicit that Amazon makes no representation about the traffic or commission income a participant can expect, so a target has to be the site's own.

The options, with their trade-offs

OptionWhat it meansTrade-off

S-23

A/B test one thing at a time, and only what the data can actually resolve

Impact: Low Effort: Medium Proposed Phase: Phase 3 — scale

The problem

The brief asks for continuous optimisation. Continuous optimisation on a site with no traffic is noise: a test on a page that receives a handful of clicks will 'win' by chance and the winner will be published as a lesson learned. Google's spam guidance also warns against creating many pages where the content makes little sense to a reader - a page matrix of near-identical variants is that problem in a different costume.

The options, with their trade-offs

OptionWhat it meansTrade-off
Option ATest only after a page has enough clicks to resolve a difference, and keep a written record of each test and its outcome.Slower. It also means saying 'not enough data' often, which is the correct answer and an unusual one to publish.
Option BGenerate variants of each article and let the optimiser pick the winner.This is scaled content abuse in a suit. Rejected.
Option CDo not test; publish the best judgement and move on.Defensible for a small site and much cheaper than A. It means optimisation never really happens.

Recommendation

Option A. The published commission rate is the same for every article in a category, so the only lever that moves earnings per click is which article a reader lands on - and that is a lever worth testing properly rather than in volume.

What this rests on

  • S38developers.google.com — Scaled content abuse, including 'creating many pages where the content makes little or no sense to a reader but contains search keywords'.
  • S04affiliate-program.amazon.com — The published commission bands.
