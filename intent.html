How each link earns a “validated” mark

The brief's rule, verbatim in effect: test one link per product in the enrolled Associates workflow, confirm destination and tracking report, before scaling.

  1. Sign in to Associates Central and open SiteStripe or the Link Builder for the declared site.
  2. Build one Special Link per product with the account's own tag (this site embeds shopnow047c-20); paste it next to the article link.
  3. Click it once and confirm the destination is the listing recorded above — same ASIN, same product.
  4. Wait for the tracking report (Reports → Earnings) to show the click attributed to this tag, then record the date on the row in docs/product-intent.json.
  5. Only then scale: a second link per product, campaign keys (DS-15), or any new product.
Until that runs, every validation cell on this page is an explicit pending — recorded as null rather than an assumed pass.

Why the two fields must never merge

An observed destination is a fact a fetch produced; an intended product is a statement only the site's owner can make. Amazon's ASIN definition gives the checkable form — a 10-character identifier — and every supplied code here is nine characters, so no code is itself an ASIN. If this register copied the observed ASIN into the intended field, it would turn an observation into an assertion nobody made. That is the same line this site holds everywhere else: a dash with a reason beats a filled-in guess. See F-01 and F-06, Q-T50-01, and the disposition questions DQ-11 / DQ-12.
