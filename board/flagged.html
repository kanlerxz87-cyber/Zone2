FL-13 high

The rule that is supposed to stop a page printing a product price never fires

What. Four copies of the context-aware price rule strip HTML tags before splitting the page into units on those same tags. After the strip there is nothing left to split on, so every page collapses to a single unit — and because almost every page mentions commission, earn or rate somewhere, the program-economics exemption then swallows any product price on it. Measured across the tree: 0 of 184 pages collapse to one unit, so the rule cannot fire on any of them.

Evidence. The inverted order is at .github/workflows/pages.yml:155, tools/validate_data.py:550, tools/build_readiness.py:623 and tools/validate_audit.py:272 - each reads re.split(r"</tr>|</p>|</li>|<br\\s*/?>", re.sub(r"<[^>]+>", " ", text)). Reversing the two operations makes the rule fire: a paragraph that offers the product at a dollar figure inside a buying context is flagged under the corrected order and passes silently under the current one. This board's own gate was written the corrected way round, and its negative test caught this very paragraph on its first run - the corrected rule works, and that is how the defect in the other four copies was noticed.

Why it matters. The site's no-prices rule is one of the four things every session asserts about every deploy. It is currently asserted by a check that cannot fail. No page is known to print a price today — this is a hole in the fence, not a breach — but the hole is in all four copies, including the one that gates every push to main.

Status. open — logged as CR-4 on the shared board, not actioned here

Owner action. In each of the four places: build the units by splitting the raw text first and stripping tags from each unit afterwards, i.e. [re.sub(r"<[^>]+>", " ", u) for u in re.split(r"</tr>|</p>|</li>|<br\\s*/?>", text)]. tools/validate_board.py already does it that way and its negative test proves the check fires. · Sources: BD-21

FL-14 medium

Two namespaces count 'tagged pages' with different rules and report different numbers

What. tools/validate_brief.py matches the tag on the bare pattern tag=[A-Za-z0-9]+-[0-9]{2}, which fires on the shape wherever it appears — including inside a sentence about tags. tools/build_board.py and tools/validate_data.py match [?&]tag=, which fires only on a real URL parameter. The two therefore disagree about the same tree, and the gap is not a rounding difference: it is whether a page that merely discusses a tag counts as carrying one.

Evidence. Observed while recording BQ2-01 on 2026-11-17. A sentence that quoted the tag as it appears in a URL was counted as a tagged page by the design-brief gate and not by this board's measurement, which reported one fewer. Two other pages in the repository — pages/flags.html and release/index.html — quote the same string in prose and are counted the same way. The sentences have been left as they are, since they are not this session's to edit; the rule is what is wrong.

Why it matters. The tagged-page count is the one number that decides whether the revenue side of this site works at all. A reader who compares the design brief's summary with the decision board's register will find two different figures and no way to tell which is right — which is how a number stops being evidence and becomes decoration.

Status. open

Owner action. Agree one rule — a tag counts only when it is a parameter of an outbound Amazon link — and apply it in both places. The sentence in BQ2-01 is the test case: it must not count. · Sources: BD-13
