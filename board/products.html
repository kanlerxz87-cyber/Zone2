Product-intent confirmation record

Two questions, two field groups, never merged

The brief asks for a record that keeps the intended product — ASIN, official listing URL, confirmation date, source — apart from what the supplied link was observed to do. That is a distinction worth keeping: one is what someone meant, the other is what a URL did. On all five rows the first group is empty and the second is full.

The rule, and why the emptiness is the finding

Product-intent confirmation record, built to the two-field rule the 2026-11-17 brief sets out: the INTENDED product (ASIN, official listing URL, confirmation date, source) and the OBSERVED redirect target are two different questions and are stored in two different objects that are never merged. The intended-product fields are empty on every row, because no value has been supplied or confirmed for them: the brief gives a link, not an ASIN, and each supplied token is 9 characters where Amazon's own definition of an ASIN is 'the 10-digit code that Amazon uses to denote specific products' (BD-12, read live 2026-11-17). A filled-in intended-ASIN field here would be an inference, so it is left blank and the row is marked UNVERIFIED. The observation fields are full: each supplied URL does resolve, reproducibly, to one live listing, and that is a fact about the link's behaviour, not about the product's identity.

The definition every token is measured against: “ASIN is the 10-digit code that Amazon uses to denote specific products.” — Amazon’s own help page, read live 2026-11-17. All five supplied tokens are 9 characters. A control confirms the two are different namespaces rather than a truncation: a valid, live 10-character ASIN placed in the same slot returns the service's “invalid URL” page. BD-05 BD-12
