Product-intent confirmation record

For each submitted link: the intended ASIN, official listing URL, confirmation date and source — in one group of fields — and the observed redirect target in a different group. The two are never merged, because they are not the same fact.

Why the split matters. Amazon's own help page defines an ASIN as “the 10-digit code that Amazon uses to denote specific products.” Every code submitted here is 9 characters, so none of them is an ASIN and none of them identifies a product on its own. Each link nevertheless resolves to one specific product page, reproducibly. Both statements are true, and publishing either one in place of the other would be a falsehood: the destination is measured, the intent is not.

How to fill a row in

  • Sign in to Associates Central and open the link report for the code.
  • Read the ASIN and the canonical listing URL it was generated against.
  • Write those into intake/data/submissions.json in the intended fields only, with the date and the report as the source.
  • Leave the observed fields alone. They are the record of what the link did on 2026-11-17, and they stay true even if the intent turns out to be different.

A gate in this namespace fails the build if an intent field is filled from an observation rather than a confirmation, or if the two groups are ever merged.
